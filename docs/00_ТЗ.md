# Техническое задание
## Учебный стенд «Поликлиника: разграничение доступа» (Supabase + Vercel)

Версия 1.0 от 15.11.2026

---

## 1. Назначение и границы

Демонстрационное веб-приложение, показывающее работу сквозного разграничения
доступа: права задаются в базе данных и действуют одинаково для интерфейса
и для прямых обращений к API. Данные синтетические; для обработки реальной
медицинской информации стенд не предназначен.

**В объёме работ:** аутентификация по паролю; три рабочие роли (администратор,
врач, пациент); три роли-заглушки; схема БД с политиками доступа; размещение
на Vercel из репозитория GitHub.

**Вне объёма:** моделирование угроз; журналирование и аудит; полный CRUD
отложенных ролей; редактирование карточек и анализов; файловые бланки;
самостоятельная регистрация и восстановление пароля; локальный стек Docker;
CI/CD-сценарии.

## 2. Роли

| Код роли | Наименование | Статус |
|---|---|---|
| `admin` | Администратор (сопоставление врачей и пациентов) | рабочая |
| `doctor` | Врач | рабочая |
| `patient` | Пациент | рабочая |
| `hr_manager` | Менеджер персонала (CRUD врачей) | заглушка |
| `patient_manager` | Менеджер пациентов (CRUD пациентов) | заглушка |
| `lab_manager` | Лаборант (CRUD анализов) | заглушка |

Один пользователь — одна роль, совмещение не предусмотрено.

## 3. Модель данных

| Таблица | Ключевые поля | Назначение |
|---|---|---|
| `doctors` | `id`, `last_name`, `first_name`, `middle_name`, `specialty`, `cabinet` | справочник врачей |
| `patients` | `id`, `last_name`, `first_name`, `middle_name`, `birth_date`, `sex`, `policy_number`, `phone`, `address` | личные данные пациентов |
| `analyses` | `id`, `patient_id`, `analysis_type`, `performed_at`, `result_value`, `unit`, `reference_range` | результаты анализов |
| `assignments` | `id`, `patient_id` (UNIQUE), `doctor_id`, `assigned_at` | действующее назначение врача |
| `app_users` | `user_id` → `auth.users`, `role`, `doctor_id`, `patient_id` | сопоставление учётной записи, роли и сущности |

Связь «врач — пациенты» логически 1:N (один врач, много пациентов; у пациента
один действующий врач). Физически она вынесена в `assignments` с ограничением
уникальности по `patient_id`: администратор управляет назначением, не имея прав
на изменение персональных данных. Повторное назначение заменяет врача.

Представления `admin_patients` и `admin_doctors` содержат только `id` и `last_name`.

**Объём фиксированных данных:** 4 врача, 8 пациентов, 24 анализа (по 3 на пациента).
Учётные записи (9): 1 администратор, 2 врача, 3 пациента, 3 менеджера. Врачи без
учётной записи остаются в справочнике и доступны для назначения.

## 4. Матрица доступа

| Роль | `patients` | `doctors` | `analyses` | `assignments` |
|---|---|---|---|---|
| `admin` | только фамилии (представление) | только фамилии (представление) | нет | чтение, создание, удаление |
| `doctor` | полные карточки назначенных пациентов, чтение | своя запись | только назначенных пациентов, чтение | чтение своих назначений |
| `patient` | своя запись, чтение | нет | нет | нет |
| заглушки | нет | нет | нет | нет |
| неаутентифицированный | нет | нет | нет | нет |

## 5. Функциональные требования

- **F1.** Вход по адресу электронной почты и паролю; выход; защита всех
  внутренних маршрутов; перенаправление на страницу входа.
- **F2.** Главная страница: сведения о пользователе (роль, фамилия) и переход
  в свой раздел. Чужие разделы недоступны.
- **F3.** Раздел администратора: два списка фамилий, форма назначения
  «пациент → врач», таблица действующих назначений, снятие назначения.
- **F4.** Раздел врача: список назначенных пациентов (ФИО, дата рождения),
  переход в карточку — личные данные и таблица анализов. Только чтение.
- **F5.** Раздел пациента: собственная карточка личных данных. Анализы и
  сведения о враче не отображаются и не запрашиваются.
- **F6.** Разделы `hr_manager`, `patient_manager`, `lab_manager`: страница
  открывается, выводится сообщение «Раздел в разработке». Данные не запрашиваются.
- **F7.** Сообщения об отсутствии прав и об ошибках — в едином оформлении.

## 6. Требования к безопасности

- **S1.** Разграничение доступа реализуется в PostgreSQL: политики RLS для
  строк, отдельные представления и привилегии — для столбцов.
- **S2.** Запрет по умолчанию: политики разрешительные, избыточные привилегии
  ролей `anon` и `authenticated` отзываются явно.
- **S3.** Роль и привязка к сущности хранятся в `app_users`; пользователь не
  имеет прав на изменение этой таблицы. Изменяемые пользователем метаданные
  (`user_metadata`) в проверках доступа не участвуют.
- **S4.** Все запросы приложения выполняются с токеном пользователя.
  Сервисный (секретный) ключ не используется ни в приложении, ни при подготовке
  данных: учётные записи создаются вручную в панели Supabase.
- **S5.** В браузер попадают только URL проекта и публичный ключ; переменные
  с префиксом `NEXT_PUBLIC_` секретов не содержат.
- **S6.** Проверка роли выполняется на сервере до отрисовки страницы.
- **S7.** Представления создаются в режиме `security_invoker`; вспомогательные
  функции проверки назначения — `SECURITY DEFINER` с фиксированным `search_path`.
- **S8.** Самостоятельная регистрация отключена.

## 7. Требования к интерфейсу

- **U1.** Сине-белая гамма: основной `#1D4ED8`, тёмный `#1E3A8A`, фон `#F4F7FE`,
  поверхности `#FFFFFF`, границы `#D6E0F5`, текст `#14213D`.
- **U2.** Типографика: системный шрифт без засечек; основной текст 16 px,
  заголовки 28/22/18 px, таблицы 15 px, подписи 14 px; межстрочный интервал 1.55.
- **U3.** Компоновка: контейнер до 1080 px, отступы 16/24 px, скругление 10 px,
  высота элементов управления 40 px, таблицы с чередованием строк.
- **U4.** Адаптивность от 360 px. Без дизайн-системы: один глобальный файл
  стилей и локальные стили страниц.

## 8. Нефункциональные требования и стек

Next.js (App Router) + TypeScript, React, `@supabase/ssr`, `@supabase/supabase-js`;
Node.js LTS. Supabase — только облачный проект, все операции с БД через веб-интерфейс
(SQL Editor, Authentication). Поддержка актуальных версий Chrome, Edge, Firefox.
Время отклика страниц — до 2 с при обычной нагрузке. Комментарии в коде —
на русском языке, поясняющие назначение и неочевидные решения.

## 9. Размещение и эксплуатация

- **D1.** Репозиторий GitHub `clinic-access-demo`; выгрузка выполняется вручную.
- **D2.** Ветка `main` — промышленная сборка Vercel, ветка `dev` — предпросмотровая.
- **D3.** Переменные окружения задаются в `.env.local` (вне Git) и в настройках
  Vercel; в репозитории — только `.env.example`.
- **D4.** SQL-сценарии хранятся в `supabase/sql/` с нумерацией по этапам,
  выполняются по порядку в SQL Editor; повторный запуск безопасен.
- **D5.** Каждый этап завершается проверяемым результатом и отдельным коммитом.

## 10. Порядок приёмки

| Проверка | Ожидаемый результат |
|---|---|
| Неаутентифицированный открывает внутренний маршрут | перенаправление на вход |
| Администратор открывает раздел | видны только фамилии; назначений — управление доступно |
| Администратор назначает врача пациенту, имеющему врача | врач заменён, дубликат не создан |
| Врач открывает список и карточку | только назначенные пациенты, данные и анализы полностью |
| Врач обращается к чужому пациенту | данные не возвращаются |
| Пациент открывает раздел | только своя карточка; анализов нет |
| Менеджер открывает свой раздел | сообщение «Раздел в разработке» |
| Проверка в SQL Editor от имени роли | набор строк соответствует матрице п. 4 |

## 11. Этапность

1. Техническое задание (настоящий документ).
2. База данных: схема → данные → учётные записи и роли → привилегии и RLS →
   политики пациента → политики врача → администратор → заглушки и сводная проверка.
3. Приложение: инициализация → ключи и клиенты → вход и защита маршрутов →
   главная и заглушки → администратор → врач → пациент → итоговая проверка.
4. Размещение: Git, переменные окружения, сборки Vercel, порядок обновления.

## 12. Допущения

Данные вымышленные, совпадения случайны. Для входа используется единый
демонстрационный пароль, задаваемый при создании учётных записей. Проект Supabase
один; предпросмотровая сборка Vercel работает с теми же данными.
