# Этап 3.4. Главная страница, шапка и разделы по ролям

**Файл документа:** `docs/stages/stage_03_4_shell.md`
**Новые файлы:** `web/src/components/AppHeader.tsx`,
`web/src/components/SectionStub.tsx`, `web/src/app/(protected)/layout.tsx`
и шесть страниц разделов
**Изменяемые файлы:** `web/src/lib/roles.ts`, `web/src/lib/auth.ts`,
`web/src/app/page.tsx`, `web/src/app/login/page.tsx`,
`web/src/app/login/actions.ts`, `web/src/app/globals.css`
**Основание:** ТЗ v1.0, раздел 5 (F2, F6, F7), 6 (S6), 7

---

## 1. Цель и результат этапа

Завершить оболочку приложения: шапка с ролью и именем пользователя, главная
страница со сведениями о пользователе и переходом в его раздел, шесть страниц
разделов с серверной проверкой роли. Три раздела отложенных ролей выводят
сообщение «Раздел в разработке».

**Результат:** после входа пользователь попадает в свой раздел; обращение
к чужому разделу приводит к странице отказа; неаутентифицированное обращение —
к странице входа. Содержательное наполнение разделов — этапы 3.5–3.7.

---

## 2. Предварительные условия

1. Этап 3.3 выполнен: вход, выход и продление сеанса работают, видимость данных
   на `/diag` совпадает с матрицей.
2. Файлы `roles.ts`, `auth.ts`, `middleware.ts` присутствуют.
3. Команды выполняются из каталога `web/`.

---

## 3. Проектные решения

| Решение | Обоснование |
|---|---|
| Группа маршрутов `(protected)` | Общий макет проверяет сеанс и рисует шапку. Скобки в имени каталога не влияют на адреса: страницы доступны как `/admin`, `/doctor` и т. д. |
| Макет проверяет сеанс, страница — роль | Разделение обязанностей: «вошёл ли пользователь» решается один раз в макете, «имеет ли право на раздел» — в самой странице вызовом `requireRole`. |
| Контекст пользователя кэшируется (`cache` из React) | Макет, шапка и страница обращаются к одному и тому же контексту; без кэша выполнялось бы три обращения к серверу аутентификации на один запрос. |
| Все шесть страниц создаются сразу | Переход по роли после входа не приводит к ошибке 404. Содержимое трёх рабочих разделов заменяется на этапах 3.5–3.7, проверка прав уже действует. |
| Заглушка — отдельный компонент | Единое оформление сообщения «Раздел в разработке» и описания назначения раздела (ТЗ, F6, F7). |
| Заглушки не запрашивают данные | Отложенные роли не имеют политик (этап 2.8); обращения к таблицам были бы бесполезны. |
| Сводка прав вынесена в модуль ролей | Текст на главной странице и в разделах берётся из одного источника и не расходится с матрицей ТЗ. |
| Переход по роли — одна функция `homeRouteForRole` | Используется и страницей входа, и серверным действием, и шапкой; расхождение маршрутов исключено. |

```ts
/**
 * Роли приложения. Перечень соответствует перечислению public.user_role в БД.
 * Модуль используется и сервером, и браузером, поэтому не содержит
 * серверных зависимостей.
 */

export const APP_ROLES = [
  "admin",
  "doctor",
  "patient",
  "hr_manager",
  "patient_manager",
  "lab_manager",
] as const;

export type AppRole = (typeof APP_ROLES)[number];

/** Проверка значения, полученного из базы данных. */
export function isAppRole(value: unknown): value is AppRole {
  return typeof value === "string" && (APP_ROLES as readonly string[]).includes(value);
}

/** Наименования ролей для интерфейса. */
export const ROLE_LABELS: Record<AppRole, string> = {

  patient_manager: "Менеджер пациентов",
  lab_manager: "Лаборант",
};

/** Раздел по умолчанию для каждой роли. */
export const ROLE_HOME: Record<AppRole, string> = {
  admin: "/admin",
  doctor: "/doctor",
  patient: "/patient",
  hr_manager: "/hr",
  patient_manager: "/patients-manager",
  lab_manager: "/lab",
};

/** Краткое описание доступных данных. Соответствует матрице доступа ТЗ. */
export const ROLE_ACCESS_SUMMARY: Record<AppRole, string> = {

  doctor:
    "Полные карточки назначенных пациентов и их анализы. Только чтение.",
  patient:
    "Собственные личные данные. Анализы и сведения о лечащем враче недоступны.",
  hr_manager: "Управление справочником врачей. Раздел в разработке.",

 * на страницу отказа с указанием причины.
```

### Шаг 3.4.2. Контекст пользователя с кэшированием (замена целиком)

Файл `web/src/lib/auth.ts`. Изменение относительно этапа 3.3 — обёртка `cache`;
содержательная логика прежняя.

```ts
import "server-only";

import { cache } from "react";
import { redirect } from "next/navigation";
import { createSupabaseServerClient } from "@/lib/supabase/server";
import { isAppRole, type AppRole } from "@/lib/roles";

/** Профиль из таблицы app_users. */
export type UserProfile = {
  role: AppRole;
  doctorId: string | null;
  patientId: string | null;
};

export type AuthContext = {
  supabase: Awaited<ReturnType<typeof createSupabaseServerClient>>;
  userId: string;
  email: string;
  profile: UserProfile | null;
  displayName: string;
};

/** Фамилия и инициалы; отчество может отсутствовать. */
function shortName(last: string, first: string, middle: string | null): string {
  const initials = [first, middle]
    .filter((part): part is string => Boolean(part))
    .map((part) => `${part[0].toUpperCase()}.`)
    .join(" ");
  return `${last} ${initials}`.trim();
}

/**
 * Текущий сеанс и профиль. Возвращает null, если вход не выполнен.
 *
 * cache() обеспечивает однократное выполнение в пределах одного запроса:
 * макет, шапка и страница получают один и тот же результат.
 */
export const getAuthContext = cache(async (): Promise<AuthContext | null> => {
  const supabase = await createSupabaseServerClient();

  // getUser() проверяет токен на сервере аутентификации.
  const { data: userData } = await supabase.auth.getUser();
  const user = userData.user;
  if (!user) return null;

  const email = user.email ?? "";

  // Профиль читается политикой «собственная строка» (этап 2.4).
  const { data: profileRow } = await supabase
    .from("app_users")
    .select("role, doctor_id, patient_id")
    .eq("user_id", user.id)
    .maybeSingle();

  const profile: UserProfile | null =
    profileRow && isAppRole(profileRow.role)
      ? {
          role: profileRow.role,
          doctorId: profileRow.doctor_id ?? null,
          patientId: profileRow.patient_id ?? null,
        }
      : null;

  // Врач и пациент читают собственную запись справочника.
  // Для остальных ролей справочники закрыты, поэтому показывается адрес.
  let displayName = email || "пользователь";

  if (profile?.role === "doctor" && profile.doctorId) {
    const { data } = await supabase
      .from("doctors")
      .select("last_name, first_name, middle_name")
      .eq("id", profile.doctorId)
      .maybeSingle();
    if (data) displayName = shortName(data.last_name, data.first_name, data.middle_name);
  }

  if (profile?.role === "patient" && profile.patientId) {
    const { data } = await supabase
      .from("patients")
      .select("last_name, first_name, middle_name")
      .eq("id", profile.patientId)
      .maybeSingle();
    if (data) displayName = shortName(data.last_name, data.first_name, data.middle_name);
  }

  return { supabase, userId: user.id, email, profile, displayName };
});

/**
 * Допуск к разделу. Применяется в серверных компонентах страниц.
 * redirect() прерывает выполнение, поэтому вызов не помещается в try/catch.
 */
export async function requireRole(
  allowedRoles: readonly AppRole[]
): Promise<AuthContext & { profile: UserProfile }> {
  const context = await getAuthContext();

  if (!context) redirect("/login");
  if (!context.profile) redirect("/denied?reason=profile");
  if (!allowedRoles.includes(context.profile.role)) redirect("/denied?reason=role");

  return { ...context, profile: context.profile };
}
```

### Шаг 3.4.3. Шапка приложения

Файл `web/src/components/AppHeader.tsx`.

```tsx
import Link from "next/link";
import { getAuthContext } from "@/lib/auth";
import { ROLE_LABELS, homeRouteForRole } from "@/lib/roles";
import { SignOutButton } from "@/components/SignOutButton";

/**
 * Шапка. Серверный компонент: роль и имя берутся из контекста запроса,
 * клиентский код не используется. Обращение к контексту повторно не
 * выполняется благодаря кэшированию (шаг 3.4.2).

export async function AppHeader() {
  const context = await getAuthContext();

  return (
    <header className="app-header">
      <div className="app-header__inner">
        <Link href="/" className="app-header__title">
          Поликлиника: разграничение доступа
        </Link>

        {context ? (
          <div className="app-header__nav">
            <span className="app-header__user">{context.displayName}</span>
            <span className="badge">
              {context.profile ? ROLE_LABELS[context.profile.role] : "роль не определена"}
            </span>
            <Link href={homeRouteForRole(context.profile?.role)}>Мой раздел</Link>
            <SignOutButton />
          </div>
        ) : (
          <div className="app-header__nav">
            <span className="app-header__user">Вход не выполнен</span>
            <Link className="btn btn--secondary" href="/login">
              Войти
            </Link>
          </div>
        )}
      </div>
    </header>
  );
}
```

### Шаг 3.4.9. Переход по роли после входа

Файл `web/src/app/login/actions.ts` (замена целиком).

```ts
"use server";

import { redirect } from "next/navigation";
import { createSupabaseServerClient } from "@/lib/supabase/server";
import { homeRouteForRole, isAppRole } from "@/lib/roles";
import type { LoginState } from "./types";

/**
 * Вход по адресу и паролю. Cookie сеанса записываются на сервере.
 * Сообщение об ошибке общее: оно не раскрывает, существует ли адрес.
 */
export async function signInAction(
  _previousState: LoginState,
  formData: FormData
): Promise<LoginState> {
  const email = String(formData.get("email") ?? "").trim();
  const password = String(formData.get("password") ?? "");

  if (!email || !password) {
    return { error: "Укажите адрес электронной почты и пароль." };
  }

  const supabase = await createSupabaseServerClient();
  const { data, error } = await supabase.auth.signInWithPassword({ email, password });

  if (error) {
    return { error: "Неверный адрес или пароль. Проверьте данные и повторите вход." };
  }

  // Роль читается из профиля тем же клиентом: сеанс уже установлен.
  const { data: profileRow } = await supabase
    .from("app_users")
    .select("role")
    .eq("user_id", data.user.id)
    .maybeSingle();

  const role = profileRow?.role;
  redirect(homeRouteForRole(isAppRole(role) ? role : null));
}
```

## 6. Проверка результата

### 6.1. Без входа

| Действие | Ожидаемый результат |
|---|---|
| Открыть `/` | Шапка «Вход не выполнен», карточка входа, таблица ролей |
| Открыть `/admin` | Перенаправление на `/login` |
| Открыть `/hr` | Перенаправление на `/login` |
| Открыть `/patient` | Перенаправление на `/login` |

### 6.2. Вход по каждой роли

| Адрес | Адрес после входа | Имя в шапке | Содержимое раздела |
|---|---|---|---|
| `clinic.admin` | `/admin` | адрес почты | «Раздел реализуется на этапе 3.5» |
| `clinic.doctor1` | `/doctor` | Соколова И. П. | «Раздел реализуется на этапе 3.6» |
| `clinic.doctor2` | `/doctor` | Ковалёв Д. А. | то же |
| `clinic.patient1` | `/patient` | Абрамова Е. В. | «Раздел реализуется на этапе 3.7» |
| `clinic.hr` | `/hr` | адрес почты | **«Раздел в разработке.»** |
| `clinic.pm` | `/patients-manager` | адрес почты | **«Раздел в разработке.»** |
| `clinic.lab` | `/lab` | адрес почты | **«Раздел в разработке.»** |

Администратору и менеджерам фамилия не показывается: справочники для этих ролей
закрыты, и приложение не пытается их читать. Это соответствует матрице доступа.

### 6.3. Обращение к чужому разделу

| Пользователь | Открываемый адрес | Ожидаемый результат |
|---|---|---|
| `clinic.patient1` | `/admin` | `/denied?reason=role`, сообщение «Раздел недоступен для вашей роли.» |
| `clinic.patient1` | `/doctor` | то же |
| `clinic.doctor1` | `/admin` | то же |
| `clinic.hr` | `/lab` | то же |
| `clinic.admin` | `/doctor` | то же |

На странице отказа отображаются имя пользователя и его роль, кнопки «На главную»
и «Выйти».

### 6.4. Главная страница вошедшего пользователя

Открыть `/`. Ожидается: шапка с именем и ролью, карточка «Ваш раздел» с описанием
доступных данных и кнопкой перехода. Ссылок на разделы других ролей нет.

### 6.5. Выход

Нажать «Выйти» в шапке. Ожидается переход на `/login`, шапка на главной
показывает «Вход не выполнен», защищённые адреса вновь перенаправляют на вход.

### 6.6. Сборка и стиль кода

```bash
npm run build
npm run lint
```

Ожидается успешное завершение. Все страницы разделов отмечены как динамические.

### 6.7. Просмотр кода заглушек

В файлах `hr`, `patients-manager`, `lab` отсутствуют обращения к таблицам:
единственный запрос данных выполняется в общем контексте (профиль и, при
наличии, собственная запись справочника).

## 7. Диагностика типовых отклонений

| Наблюдение | Причина | Действие |
|---|---|---|
| После входа ошибка 404 | Не созданы страницы разделов | Выполнить шаги 3.4.6–3.4.7 |
| Бесконечные переходы `/login` ↔ раздел | Макет и страница используют разные источники сеанса | Убедиться, что применяется `getAuthContext` из `lib/auth.ts` |
| Шапка отображается дважды | Страница дополнительно рисует `AppHeader` | В разделах шапку не добавлять: она в макете |
| Ссылки в шапке синие на синем | Не добавлены стили шага 3.4.10 | Дополнить `globals.css` |
| Ошибка «requireRole в клиентском компоненте» | Страница помечена `"use client"` | Убрать директиву: страницы серверные |
| Три обращения к аутентификации на запрос | Не применена обёртка `cache` | Заменить `auth.ts` по шагу 3.4.2 |
| Каталог группы попал в адрес (`/(protected)/admin`) | Скобки заменены обычными символами | Имя каталога — ровно `(protected)` |
