# Этап 2.2. Наполнение фиксированными данными

**Файл документа:** `docs/stages/stage_02_2_seed.md`
**Файл сценария:** `supabase/sql/02_2_seed.sql`
**Основание:** ТЗ v1.0, разделы 3 (объём данных), 9 (D4), 12

---

## 1. Цель и результат этапа

Загрузить фиксированный синтетический набор данных: 4 врача, 8 пациентов,
24 анализа (по 3 на пациента) и 5 стартовых назначений. Сценарий выполняется
повторно без появления дублей и без ошибок.

**Результат:** таблицы наполнены; три пациента оставлены без врача — они
предназначены для демонстрации работы администратора на этапе 3.5.

**Чего на этом этапе нет:** учётных записей, ролей в `app_users`, политик доступа.
Таблицы остаются закрытыми для клиентских ролей (проверка 5.5 этапа 2.1).

2. Открыт **SQL Editor** проекта Supabase.
3. В репозитории создан файл `supabase/sql/02_2_seed.sql`.

## 3. Принципы наполнения

| Принцип | Реализация |
|---|---|
| Детерминированность | Идентификаторы задаются явно по фиксированной маске. Повторное прохождение этапов даёт те же ссылки, что упрощает проверку политик и отладку. |
| Повторяемость | `insert ... on conflict ... do update`: строка либо создаётся, либо приводится к эталонному состоянию. |
| Синтетичность | Фамилии, адреса, полисы и телефоны вымышлены; город условный. Реальные персональные данные не используются. |
| Разделение ответственности | Сценарий не создаёт учётные записи: это этап 2.3, выполняемый через панель Supabase. |
| Управляемые назначения | Стартовое распределение задаётся здесь, дальнейшее изменение — только администратором через приложение. |

### 3.1. Маска идентификаторов

| Сущность | Маска | Диапазон |
|---|---|---|
| Врачи | `11111111-1111-4111-8111-1111111111NN` | `01`–`04` |
| Пациенты | `22222222-2222-4222-8222-2222222222NN` | `01`–`08` |
| Анализы | `33333333-3333-4333-8333-3333333333NN` | `01`–`24` |
| Назначения | `44444444-4444-4444-8444-4444444444NN` | `01`–`05` |

Формат соответствует версии 4 и варианту RFC 4122, поэтому значения принимаются
типом `uuid` без замечаний.

### 3.2. Плановое распределение (согласуется с этапом 2.3)

| Врач | Пациенты | Учётная запись врача |
|---|---|---|
| Соколова И. П., терапевт | Абрамова, Борисов, Васильева | будет создана |
| Ковалёв Д. А., кардиолог | Григорьев, Дмитриева | будет создана |
| Никитина О. С., эндокринолог | — | не создаётся |
| Гаврилов П. Н., невролог | — | не создаётся |

Пациенты **Ерохин, Жукова, Зайцев** остаются без назначений. Учётные записи
пациентов будут созданы для Абрамовой, Борисова и Дмитриевой: первые две
обслуживаются одним врачом, третья — другим, что позволяет проверить изоляцию
списков на этапе 2.6.

### Шаг 2.2.4. Стартовые назначения

Ключ конфликта — `patient_id`, то есть ограничение «один действующий врач
на пациента». Именно эта конструкция будет использоваться в интерфейсе
администратора при переназначении.

Поле `assigned_by` задаётся пустым намеренно: назначения создаёт сценарий,
а не пользователь. При работе через приложение оно заполнится значением
`auth.uid()` автоматически.

> **Внимание.** Повторный запуск этого блока возвращает стартовое распределение
> и перезаписывает изменения, внесённые администратором. После начала работы
> с приложением блок 2.2.4 повторно не выполняется.

## 5. Проверка результата

### 5.1. Количество записей

```sql
select
  (select count(*) from public.doctors)     as doctors,
  (select count(*) from public.patients)    as patients,
  (select count(*) from public.analyses)    as analyses,
  (select count(*) from public.assignments) as assignments,
  (select count(*) from public.app_users)   as app_users;
```

Ожидается: `4`, `8`, `24`, `5`, `0`.

### 5.2. Полнота анализов по пациентам

```sql
select p.last_name, count(a.id) as analyses_count
from public.patients p
left join public.analyses a on a.patient_id = p.id
group by p.id, p.last_name
order by p.last_name;
```

Ожидается 8 строк, в каждой — `3`.

### 5.3. Распределение пациентов по врачам

```sql
select d.last_name as doctor, d.specialty, count(a.patient_id) as patients_count
from public.doctors d
left join public.assignments a on a.doctor_id = d.id
group by d.id, d.last_name, d.specialty
order by d.last_name;
```

| Врач | Пациентов |
|---|---|
| Гаврилов | 0 |
| Ковалёв | 2 |
| Никитина | 0 |
| Соколова | 3 |

### 5.4. Пациенты без назначения

```sql
select p.last_name
from public.patients p
left join public.assignments a on a.patient_id = p.id
where a.id is null
order by p.last_name;
```

Ожидается: `Ерохин`, `Жукова`, `Зайцев`.

### 5.5. Повторяемость сценария

Выполните блоки 2.2.1–2.2.4 ещё раз и повторите проверку 5.1.
Ожидается прежний результат `4, 8, 24, 5, 0` — признак корректной идемпотентности.

### 5.6. Контроль ограничения «один врач на пациента» (необязательно)

Проверка выполняется в транзакции с последующей отменой, данные не изменяются.

```sql
begin;

insert into public.assignments (patient_id, doctor_id)
values ('22222222-2222-4222-8222-222222222201', '11111111-1111-4111-8111-111111111102');
```

Ожидаемое сообщение: `duplicate key value violates unique constraint
"assignments_one_doctor_per_patient"`. После ошибки выполните отдельным
запросом `rollback;`.
